IRIS Phase 1 Audit

A read-only survey of the IRIS codebase against the newly supplied Brand Identity Pack and avatar references — what is strong, what is incomplete, what is fragile, and what must not be touched.

Date 4 September 2026 Repo iriss-main Engine src/iris · 2,897 lines Tests 55 unit · 189 harness

The short version

The engine is the strongest part of this product and should be left alone. It is deterministic, diagnosis-blind, specification-traceable, and covered by a build-breaking test. Everything downstream of it is weaker, and the gap that matters most is new: the Brand Identity Pack has never been applied. Not one of its six palette values appears anywhere in the source, the shipping logo is a corrupted variant, and the mascot resembles neither avatar reference.

Separately, one legacy screen contains fabricated doctors, ratings and testimonials. It is currently unreachable through the UI but is still routed and still compiled into the bundle. That is the single highest-risk item in the repository.

ACurrent architecture

Three layers, cleanly separated, with one deliberate seam between them.

Frontend
React 18 + TypeScript, Vite 6, Tailwind v4 (CSS-first — there is no tailwind.config.js), Motion v12 for animation, shadcn/ui primitives.
Engine
Plain JavaScript in src/iris/, 2,897 lines across 15 modules. No React, no DOM, no I/O — pure functions over data.
Backend
Express 4 + Sequelize 6 + SQLite. 18 routes. Bearer tokens, SHA-256-hashed sessions in the database.
State
Four React contexts: AppContext (legacy), IrisContext (engine), LanguageContext, AudioContext.

The seam worth knowing: the React layer touches the engine through exactly one module, IrisContext.tsx, which imports six functions from iris/journey.js. Two screens bypass it — BlindnessDemoScreen reaches into iris/demo/scenarios.js, and IrisParentChat into iris/parent/chatbot.js — both read-only. Twelve components consume useIris(); none import an engine directly. That discipline is why the engine has survived four passes of UI churn intact.

Incomplete

There are two generations of app living side by side. The new IRIS flow (IrisFlow, IrisChildHome, IrisActivityScreen) is what runs; roughly 25 legacy screens remain imported and routed. ChildModeScreen is imported but never rendered. The legacy island is reachable only from ParentDashboardScreen, which nothing now navigates to.

BCurrent UI structure

Entry is IrisLanding → two doors: Child Mode and Parent Mode.

Child Mode gates on a name, then IrisChildHome offers one primary action (“Start Adventure” → screening → activities) and five free-play tiles: Memory Game, Balloon Pop, Shadow Match, Stories, Drawing. A “Committee demo (scenarios A/B/C)” entry sits on the gate screen.

Parent Mode is authenticated — login, or a three-step registration wizard carrying the consent checkbox. Behind it, five sections: Progress & Insights and Home Tips and Ask IRIS are live; Parent Community and Connect with Specialists are marked Soon.

ChildShell supplies a floating identity pill (avatar, name, star count) to the 19 legacy child screens. The four new IRIS-flow screens render their own headers instead — so two header conventions coexist.

Improve

Five different page widths are in use (max-w-6xl ×18, 4xl ×18, 2xl ×13, 3xl ×10, plus six others) with no shared container. Breakpoints are effectively two: md: ×71, lg: ×25, sm: ×15, and no xl: at all — the 640–768px band is barely addressed. Twenty-two fixed elements share a hand-rolled z-stack, three of them competing for the top strip.

CCurrent design system

There are two token sets, and the screens use neither.

src/styles/iris.css defines 13 IRIS tokens — --iris-primary: #7c3aed (violet), four accents, ink, surface, a 44px touch floor. src/styles/theme.css defines the full shadcn set including --primary: #030213 (near-black) and a complete .dark block. The two disagree about what the brand colour is, and .dark is never toggled by anything.

Searching for var(--iris-…) outside src/styles/ returns no hits at all. Components hardcode Tailwind utilities instead. The actual colour distribution across src/App/components:

Critical — brand

None of the six brand palette values appear anywhere in src/. Verified by direct search: #FECA34 0, #1F67B1 0, #F45B63 0, #49B87A 0, #8060B4 0, #FEF6EA 0. The product reads as a purple-and-slate SaaS app; the brand pack specifies warm white with a bright five-colour system, organic blobs and hand-drawn marks. The pack is dated today — the app simply predates it.

Critical — asset

The logo shipping in public/images/iris-logo-static.png is the degraded variant. Its tagline renders as “coaurge”, not “courage”, and “hope” / “Wisdom” are illegible squiggles. The clean master — with all three words correct — exists at IRIS_Brand_Identity_Pack/assets/IRIS_logo_master.png and was never copied into the repo. This is on the landing page a judge sees first.

Typography is the one area already aligned with the brand: Quicksand for Latin, Cairo/Tajawal for Arabic with line-height: 1.75 and a letter-spacing: 0 !important override to defeat Tailwind tracking on Arabic — a real, correct detail. All three load by CSS @import from Google Fonts, so they fail silently offline. Nunito is named in the fallback stack but never imported.

DCurrent avatar implementation

Two files, not two characters. IrisBuddy.tsx is the artwork: hand-authored SVG on a 120×120 viewBox — five petal ellipses in a #A78BFA → #F0ABFC violet gradient, a #FFFDF8 face circle stroked #C4B5FD, #FBCFE8 cheeks, features in #3B2A5A. Five moods: idle, happy, celebrate, thinking, encourage — and deliberately no sad or disappointed state. IrisMascot.tsx wraps it with Motion float/bounce, a mood glow and a speech bubble, and is the only public entry point. It renders in five places. Neither is dead code.

The engineering is sound. The problem is that it is the wrong character.

Critical — brand

Both avatar references are warm, plush, three-dimensional figures with cream bodies, multi-coloured petals in the brand red / blue / green / yellow, and a transparent heart window holding sparkles. The implemented mascot is a flat, single-hue violet flower. It shares no colour, no material and no silhouette with either reference. Violet is not in the brand palette at all — the closest is #8060B4, used for imagination, not as the identity colour.

The child-facing avatar picker is separate and is emoji, not drawn art: 10 fixed options (🦊 🐼 🐸 🦁 🐨 🐧 🦋 🐢 🌟 🚀) stored in React state only — the choice is lost on refresh.

ECurrent chatbot behaviour

Rule-based, not an LLM, and honest about it. Three stages: four safety routes (medical, diagnosis, emergency, therapy plan) that always run first and always win; three live-data intents answered from the child's own session record; then keyword retrieval over a 12-entry knowledge base. Every answer carries an evidence tier and a source. Unknown questions return “I do not have an approved answer … and I will not invent one.” It is structurally incapable of fabricating — it can only return strings already present in guidance.js, and assertSafeText() throws on any banned term.

Improve — two regex over-triggers

Both confirmed by running the patterns. The unanchored iq in the diagnosis route matches inside ordinary words, so “What is a unique activity for him?” is refused as a diagnosis question. And the Arabic medical route matches bare نوم (sleep), so any bedtime question is refused — while the English side correctly matches only sleep apnea|snoring. The safety behaviour is right; the boundary is drawn too wide, and asymmetrically between languages.

Twelve entries is also thin for a free-text box. It will miss more than it hits, and the honest fallback — while correct — is what most parents will see.

FCurrent assessment logic

Nine tasks, one per sub-measure, identical for every child — there is no adaptive item selection, by design. Seven are stepped (3–4 items per step, three steps), two continuous. Scoring is DPS = 100 × (0.5·accuracy + 0.3·depth + 0.2·independence). Stop rules: advance a step at ≥2 correct, discontinue after 2 consecutive wrong within a step, minimum 3 scoreable items. Rapid responding (<600ms, >30% of items) and timeouts (>25%) raise data-quality flags rather than altering the score.

Crucially, the engine returns dps: null and notDetermined: true rather than a zero when it lacks evidence. There is no “untestable child” state — only undetermined data. The intro screen states plainly that this is not an intelligence test and does not diagnose.

Fragile — spec drift

The specification allows up to 112 items; the shipped screen presents a fixed linear run of 44 with no early stop. Two sub-measures (LANG.INSTRUCTION, VSP.PATTERN) ship one item per step while the advance threshold is two, so highestStepPassed is structurally 0 and depth is always 0 — costing up to 30 DPS on those measures. The attention tasks are declared continuous with 20 trials but present 4 items and send no false-alarm or time-on-task rows, so depth silently defaults to 1. Scores are being produced from a shape the scorer was not written for.

Practical consequence for the demo: answering poorly, the screening ran ~45 items before reaching a result in testing. That is too long to show live.

GCurrent adaptive logic

This is the best-built part of IRIS. Eleven numbered rules in a strict cascade, every decision stamped with a rule ID, reason code, rule-pack version and a fixed bilingual parent explanation. No LLM anywhere in the decision path.

Strong — verified

Diagnosis blindness holds. Across src/iris/, a diagnosis value is read in exactly one functional place: accommodationDefaults() in journey.js, which returns access accommodations and declares never_affects: ['scoring','item_selection','difficulty','level','goal_selection','pathway']. scoreAssessment, buildProfile, selectGoals, decideNext and generateActivity have no condition parameter at all — it is structurally out of scope. The demo confirms it end to end: five diagnoses, identical performance, identical goal, level, pathway and next activity.

Critical — latent

Modality shift is broken for three of its four declared pairs. R-PATH-006 checks only that modality_pair_id exists — it never verifies the partner template serves the current goal and level. TPL-SEQ_VERBAL ↔ TPL-SEQ_VISUAL cross different goals; TPL-PICK_PICTURE (L1–3) and TPL-PICK_WORD (L4) never overlap on level. When one of those fires, servableItems() returns an empty array and the validator rejects the activity. Only TPL-SOUND_MATCH ↔ TPL-SOUND_MATCH_PICTURE_LED is safe — and that is the pair the demo happens to exercise.

Fragile — content depth

The bank holds exactly 3 items per goal/level/template (87 total) while item_count defaults to 6, so every activity is silently 3 items and the variant seed only reshuffles the same three. A child who repeats a level sees identical content. Reduction is also applied twice — journey.js computes 4, then generateActivity reduces again to 3.

HCurrent voice / TTS flow

The path is: any of 76 speak(text, lang) call sites → AudioContext.speak() → voice.ts getClip() → POST /api/tts → server/routes/tts.js → ElevenLabs → MP3 blob → one reused <audio> element. The API key stays server-side and is absent from the built bundle (checked). Language selects the voice server-side; nothing in the UI picks a voice.

Guarantees that hold under test: narration cannot overlap itself (one reused element), mute stops it immediately, leaving a screen stops it, each distinct line is fetched once per session and cached on disk server-side, and every failure mode — missing key, bad key, 429, dead network, over-long text — degrades to browser speech synthesis rather than to silence.

Unresolved

The live ElevenLabs call has never succeeded on the target machine: server/.tts-cache/ is empty, and the cache is written on every success. The diagnostic scripts/check-voice.mjs was built to name the cause and has not yet been run. Until it is, narration is running on the browser fallback voice.

ICommunity & specialists

The new sections are exemplary. IrisCommunity shows four deliberately unattributed topic tiles and states “Nothing here is a real post or a real parent's words.” IrisSpecialists shows four category cards with every call-to-action disabled, and states “There are no real practitioners, appointments, or bookings here.” No names, no credentials, no ratings, no counts.

Critical — highest risk in the repo

The legacy CommunitySessionsScreen.tsx does the opposite of all of it. It contains four invented doctors with names, credentials, ratings and review counts (Dr. Sarah Ahmed … rating: 4.9, reviews: 127), fabricated availability slots, three fabricated parent testimonials with like counts, and a live booking POST to /api/bookings against a real backing table. FamilyGuidanceScreen.tsx adds eight uncited articles including nutrition and sleep advice, plus a non-functional “AI Parent Assistant”.

Both are unreachable by navigation today — the only route in is ParentDashboardScreen, which nothing links to — but both are still imported, still in the Screen union, still in the router switch, and still compiled into the shipped bundle. One stray navigateTo('community-sessions') puts fabricated medical credentials in front of a judge.

JDatabase structure

Seven tables: Users, Children, Sessions, AssessmentRecords, ActivitySessions, Posts, Bookings.

Auth
Passwords bcrypt cost 12. Session tokens stored as SHA-256 hashes with a BIGINT expiry, purged hourly. requireAuth on every protected route, requireSelf on email-scoped routes, requireConsent on every mutating route.
Engine records
ActivitySessions stores the full decision trail — decision_rule_id, decision_reason_code, decision_payload, rule_pack_version. Every synthetic row carries is_synthetic.
JSON columns
item_results, domain_scores, accommodations are TEXT holding stringified JSON.
Fragile

There are no Sequelize associations anywhere — no hasMany, no belongsTo, no references. user_id and child_id are bare integers, so there is no referential integrity and no cascade on delete; ownership is enforced only by hand in each route (correctly, today). Deleting a parent orphans their child rows silently. Separately, POST /api/posts and POST /api/bookings spread ...req.body straight into create() — a client can set likes to anything it likes.

condition is stored on both Users and Children. Only the Children copy should matter; the duplicate invites drift.

KExisting tests

55 unit tests in one file, tests/iris.test.js (653 lines), run by node --test. Coverage is deep where it matters: 4 diagnosis-blindness tests including TEST-PATH-BLIND, 3 determinism tests (one runs 50 repetitions), 4 mastery tests, 8 adaptation-ordering tests, 4 DPS tests, 4 profile tests, 11 content and validator tests, 6 parent-safety tests, and 4 end-to-end scenarios.

Alongside them, 189 harness checks across nine Playwright and API suites — accessibility 16, integration 15, audio 14, stories 18, TTS route 19, voice client 19, security 29, journey 42, demo/visual 10, resilience 7.

Gap

There is no test at any level that would catch the three defects this audit found. Nothing asserts the brand palette is used, nothing renders a React component in isolation, and nothing asserts that fabricated-content screens are absent from the bundle. The suite proves the engine is correct; it does not yet protect the product's honesty or its identity.

Assessment

Already strong — protect it

  • The adaptive engine: deterministic, traceable, diagnosis-blind, and proven so by a build-breaking test.
  • Auth and consent: bcrypt 12, hashed DB-backed sessions, no user enumeration, consent gate on every mutating route, the old user-dump endpoint returning 410.
  • Claim discipline in new code: the screening intro, landing disclaimer, parent-mode footer and chatbot refusals are the most careful part of the writing.
  • Accessibility: captions on every spoken line, reduced motion honoured in both CSS and JS, 44px touch floor, zero horizontal overflow at 390/820/1440.
  • Offline resilience: Child Mode and Stories work fully with the backend stopped.

Incomplete

  • The brand pack is unapplied — palette, shapes, and the correct logo asset.
  • Community and Specialists are honest placeholders, not features.
  • The chatbot knowledge base is 12 entries against a free-text input.
  • Content depth: 3 items per goal/level means repeats show identical material.
  • No persistence in IrisContext — a refresh discards the profile, goals, stars and avatar choice.

Fragile

  • AppContext.reportPerformance still calls CognitiveEngine.evaluateAndAdapt(), which now throws, on every fifth report. Reachable only from legacy screens that nothing currently links to.
  • Modality shift produces invalid activities for three of four template pairs.
  • Assessment UI and scorer disagree about item counts and step structure.
  • Two heavy neutral ramps and three ramps each for green and amber — a restyle will be slower than it needs to be.

Must not be touched

  • src/iris/engines/*Scoring, profile, goals, pathway, progress. The rule cascade and its ordering are the product.
  • src/iris/journey.jsEspecially accommodationDefaults() — the one permitted diagnosis read.
  • tests/iris.test.jsExtend if you must; never weaken an assertion to make a change pass.
  • server/server.js authSession hashing, consent gate, requireSelf, the 410 on /api/users.
  • Claim-safety copyScreening intro, landing disclaimer, chatbot refusals, specialist and community labelling.
  • src/iris/content/validator.jsThe banned-term and diagnosis-name gate on child-facing content.

Recommended implementation order

Ordered by risk removed per unit of effort, and by what unblocks what. Steps 1–3 are small and should happen before anything visual.

  1. Delete the fabricated-content screens

    Remove CommunitySessionsScreen, FamilyGuidanceScreen, their routes, their Screen union entries, and the /api/bookings route and table.

    Highest risk, lowest effort, no dependencies. Nothing links to them, so nothing breaks — and it removes the only thing in the repo that could seriously damage credibility.

  2. Swap in the correct logo

    Copy IRIS_logo_master.png into public/images/ and repoint IrisLanding.

    One file. Fixes a misspelling on the first screen anyone sees.

  3. Run the narration diagnostic

    node scripts/check-voice.mjs, then act on whichever step it stops at.

    Five seconds, and it settles whether the voice work is finished or still blocked. Cheap to do before committing to anything else.

  4. Retire the legacy island

    Remove the remaining orphaned screens and the dead CognitiveEngine call sites in AppContext.

    Do this before the restyle, not after — every screen deleted now is a screen you do not have to re-theme. It also removes the throwing code paths.

  5. Establish the brand token layer

    Collapse iris.css and theme.css into one set built on the six brand colours plus a chosen warm neutral ramp. Do not migrate components yet — just make the tokens correct and real.

    Everything visual downstream depends on this. Doing it after the deletions means fewer consumers to migrate.

  6. Redraw the avatar

    Rebuild IrisBuddy's artwork to the references — cream body, brand-coloured petals, heart window with sparkles. Keep the five moods, the props, and the rule that there is no sad state.

    Self-contained: one file, one render site through IrisMascot. It is also the most visible single change, and it validates the new token layer on real artwork.

  7. Migrate screens to the tokens

    Child Mode first, then Parent Mode, then the remaining shared components. Collapse slate/gray to one neutral and emerald/green/teal and amber/yellow/orange to one each as you go.

    The bulk of the visual work, and the part that benefits most from steps 4 and 5 being done first.

  8. Fix modality shift

    Make R-PATH-006 verify the partner template serves the current goal and level before shifting; fall through to backstep when it does not.

    A real correctness bug in the engine's cascade. It sits this far down only because it is currently masked — the demo path uses the one pair that works. Add a test that walks every declared pair.

  9. Reconcile the assessment screen with the scorer

    Wire the existing stop rule to the screen, align item counts per step, and emit the missing attention rows.

    Shortens the screening to something demonstrable and stops the scorer being fed a shape it was not written for. Touch the screen, not the scoring.

  10. Persist child state

    Write profile, goals, stars and avatar through to the existing backend tables, with localStorage as the offline fallback.

    Turns the parent dashboard from a within-session view into a real record. Depends on nothing above, but is more valuable once the rest is stable.

  11. Tighten the chatbot, then grow it

    Word-boundary the iq pattern and narrow the Arabic sleep term; then expand the knowledge base from the research corpus.

    The two regex fixes are minutes. Growing the KB is open-ended, so it goes last.

Deliberately not in this list: the database association work and the mass-assignment whitelist. Both are real, neither is visible, and neither blocks anything else — they belong in a maintenance pass after the identity work lands.
